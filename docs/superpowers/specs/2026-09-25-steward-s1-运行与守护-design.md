# S1 · 运行与守护 —— 设计

产品：昱弘设备管家 Yuhox Steward　slug `steward`　许可 PolyForm Noncommercial 1.0.0
本批范围：能力矩阵 A 组全部 + 权限模型与动作登记（后续各批都复用）。
能力口径以 `docs/能力矩阵.md` 为准，本文件不重复定义，只定义**怎么实现、怎么算做到**。

## 1. 本批要立住的东西

一句话：**人不在，机器照常干活；活干完，机器自己停。**

这是全网开源里没有的组合。`KeepingYouAwake`（6.9k★，活跃）只做常亮；
`Amphetamine` 闭源且合盖模式要外接屏；`Crisp`（MIT，活跃）做虚拟显示器但不碰休眠策略；
`Mole` / `Stats` / `Pearcleaner` 根本不在这个域。而且**它们全是 macOS 单平台**。

所以 S1 不是"第一个里程碑凑合做个小的"，S1 就是这个产品的名字。

## 2. 能力与验收口径

每条都给可数的验收，不给"基本可用"这种话。**没跑过的条目一律标 `待实测`，不许写进对外文案。**

### 2.1 防自动休眠（常亮）

- 实现：IOKit 电源断言 `IOPMAssertionCreateWithName`，类型 `kIOPMAssertionTypePreventUserIdleSystemSleep`，
  可选叠加 `...PreventUserIdleDisplaySleep`（屏幕常亮）。断言由**常驻的 Go 核心进程**持有，
  进程退出即自动释放 —— 这是安全性质，不是实现细节：核心崩了不会留下一个永不休眠的机器。
- 验收：`pmset -g assertions` 输出中出现我们的断言行，且 `pid` 属于 steward 核心进程；
  杀掉核心后 5 秒内该行消失。空闲 30 分钟不休眠，撤掉后按系统设置正常休眠。
- 不需提权。

### 2.2 合盖不休眠

- 现状（本机实测，M4 Max / macOS 15.6）：`pmset -g` 里有 `SleepDisabled 0` 这个系统级设置项，
  但 `pmset(1)` 的 man page **不记载它**；`caffeinate` 的全部参数（`-d -i -m -s -u -t -w`）
  只管 idle / disk / display / AC 系统睡眠，**没有任何一项管合盖**。
  结论：断言这条路堵死，必须走 `sudo pmset -a disablesleep 1`，即**必须提权**。
- `部分实测（阻塞项已解开一半）`：**disablesleep=1 能挡住合盖触发的睡眠** ——
  本机已有一次 **82 秒合盖、零睡眠事件、flag 全程未回落**的实测，老板侧远程会话同样没断（详见 §7）。
  还欠一次**满格档**：口径收紧为"合盖这段时间里 `SleepDisabled=1` 连续覆盖 ≥ 窗口 80%
  （3 分钟档即 ≥132 秒）且零睡眠事件" —— 现在最强的一轮只覆盖 82 秒，
  另一轮（21:27）工具把标志提前还原了，开着的时间只有 2 秒，所以都不算满格。
  以及还欠**重启/待机后这个标志还在不在**（二手证据两边说法冲突）。
  在满格档补上之前，对外文案只写"合盖后保持运行"，**不写时长**；
  测不出来（满格档反而睡了）则 2.2 整条从对外文案撤掉。
  **测的口径已定：整 3 分钟保持合上，只合几秒不算数**（对照跑过一次 4 秒的，判据照样抓到，
  说明秒级可靠，但那一次的时长不足以支撑产品承诺）。
  测试口径见 §7 的合盖实测流程，需要老板在这台机器上配合动手。
  已确证的半边（不用合盖就能测）：合盖触发睡眠在这台 M4 Max 上真实发生并被记账，
  `pmset -g log` 里 `due to 'Clamshell Sleep'` 自 09-21 开机以来一直有存量（跑实验前 13 条，
  对照组每确认一次真实合盖睡眠就 +1）；
  同时 `disablesleep` / `SleepDisabled` 在苹果文档里**查无出处**（man page 只记载 `lidwake`，
  连当年讲合盖要求的 HT201834 现在都重定向到线材连接页），
  所以这是一个苹果未承诺的隐藏开关，随时可能失效 —— 这也是 §2.2 要求每次启动读实际值、
  以及三重守卫（温度/电量/登记未闭合）必须是硬约束而不是设置项的原因。
  另有一条本机读数别当依据：`ioreg` 里 `AppleClamshellCausesSleep = No`，
  而同机器日志里 Clamshell Sleep 明明在发生 —— 这个键在 Apple Silicon 上是残留字段，
  不许拿它判"这台机器合盖会不会睡"。真正可信的只有 `AppleClamshellState`（盖子开合，免密可读）。

- **机制选型的旁证（二手，非本机实测，须在 M4 Max 上复验后才能写进对外文案）**：
  Amphetamine 的 Closed-Display Mode 底层实现就是 `sudo pmset -a disablesleep 1`
  （见其 `powerProtect.scpt`），其 issue #19 是 M1 Pro / macOS 15.6 上的受控实测：
  合盖、无外接屏、0.5 秒轮询 `pmset -g`，`SleepDisabled=1` 期间不睡，一旦翻回 0 立刻
  `Entering Sleep due to 'Clamshell Sleep'`。Sleepless、Unblinking 等同族项目同结论，
  并且明确指出**断言打不过内核的合盖事件**（这与我本机核过的 caffeinate 参数表一致）。
  也就是说：不是"我们挑了这条路"，而是**这条路是唯一的**，选型与业界唯一活路对齐。
- **旁证里会改设计的四条**（除第 2 条外仍是二手，逐条要本机复验）：
  1. **会被系统偷偷重置**：Apple Silicon 上有机器在电源/显示拓扑变化后把 `SleepDisabled`
     自行改回 0，导致合盖/维护睡眠循环，有项目为此**每 2 秒重设一次**。
     → 实现不能是"开一次就完"，必须在活动期内持续重设并**把被重置次数计给用户看**；
     否则界面上写着"合盖保护已开启"而实际早就失效，是我们自己无法辩护的那种事故。
     本机已实测**排除秒级重置**（82s 与 177s 两轮里 2 秒一采，flag 一次都没自己跳过），
     但"接电源 / 拔屏 / 换显示拓扑"这三种触发条件本机还没造过，仍待复验。
  2. **还原不补睡 —— 这条已由本机实测坐实（2026-09-25 21:27，M4 Max）**：
     合盖那一刻 `SleepDisabled=1`，13 秒后被工具写回 0，盖子继续合着 **172 秒**，
     期间 `due to 'Clamshell Sleep'` **14 → 14 零新增**、心跳 292 个采样最大间隔 **2 秒**。
     也就是苹果只在合盖那一下判一次，之后翻标志不会补算事件，机器会带着"合盖不睡"
     醒着待在包里直到没电。
     → 守卫里的"还原"必须是**还原 + 合盖状态下补一次 `pmset sleepnow`**，
     否则 §2.2 那三重守卫在这个最典型的场景下是假的。已按此实现（留 10 秒开盖反悔窗）。
     副产品一条产品口径：**"合盖保护"生效与否，取决于合盖那一瞬间标志在不在**，
     不是"这段时间里开过就行" —— 所以界面上"当前是否在保护中"要按实时取值显示，不能按开关历史显示。
  3. **读值不许假设键存在**：macOS 26 arm64 上取值为 0 时 `pmset -g` 可能整行不打印。
     → 判定一律写成"缺键视为 0"，验收口径同理（不能写 `grep SleepDisabled` 空输出就算失败）。
  4. **关键电量仍强制睡、且散热从转轴走**：合盖满载没有风道，是反复出现的告警主题。
     → 温度/电量阈值必须按"合盖 = 更差散热"重新标定，不许沿用开盖阈值，
     这条进了 §5.2 的合盖热降频实测。
- **验收是双口径的，只过一条不算过**：
  ① 机制口径 —— 窗口内 `due to 'Clamshell Sleep'` 零新增、心跳零断档、
     且 `SleepDisabled` 全程未被重置（三项都由 `tools/lidprobe` 自动出）；
  ② 产品口径 —— **老板那条远程会话整程不掉线**。
  两者可能不一致：合盖掉线也可能是显示/网卡那一路被关而机器并没睡，
  那种情况下 `disablesleep` 修不好它，而"远程连上一台合盖的 Mac"恰恰是这个功能的全部卖点。
  所以实验组的报告里"远程会话断没断"是必填项，不允许只交日志。
- 安全守卫（做成硬约束，不是设置项）：开启 disablesleep 期间，
  ① 温度超阈值 → 告警并**无条件还原**；② 电量低于阈值且未接电源 → 告警并还原；
  ③ 核心退出 / 崩溃 → 下次启动检测到登记未闭合，立刻还原。
  理由：合盖塞进包里持续满载是真会把机器烧坏的，这条不做等于埋雷。
  三处的"还原"均按上面第 2 条理解为"写回 0 + 合盖则补睡"。
- 验收：开→`SleepDisabled` 为 1（缺键视为 0，见第 3 条）；关→为 0；
  异常退出后重启软件，值为 0（回滚路径必须实测，不能只测正常路径）；
  以及上面双口径那两条同时成立。

### 2.3 无头 / 虚拟显示器

- 实现：创建虚拟显示器，让系统在没接屏的情况下仍有可渲染的显示目标。
  参照 `Crisp`（MIT）的做法，它已证明**开源可实现、常规路径免密码**
  （它需要密码的只有 smooth scaling 那个 display override 文件，与虚拟显示器无关）。
  这块落在 `helpers/macos/` 的 Swift 里（私有 CoreGraphics / CoreDisplay）。
- 先修口径：能力矩阵里这条我标的是「部分」，实测依据到位后升 `✓`，**改矩阵要单独一次提交**。
- 验收（必须是生产口径，不是开发口径）：同一份 Metal / ffmpeg 硬件编码任务，
  在①接屏 ②拔屏 ③合盖+虚拟显示器 三种条件下跑，**输出帧数与耗时一致**（±2%）。
  只测"能不能建出显示器"不算过 —— 建出来但渲染不出来是最可能的失败模式。

### 2.4 任务跑完自动休眠

- 触发条件四类，都要能组合：进程退出（按 pid 或按名字）/ CPU 与磁盘持续低于阈值 N 秒 /
  指定文件出现或达到指定大小 / 我们自己起的命令返回。
- **失败也要触发**：任务报错退出时同样执行动作，否则整夜等一个永远不会来的成功。
  这条单独测，因为它是最容易做漏的。
- 动作：休眠 / 关机 / 仅撤销常亮 / 只通知。默认留 60 秒可取消窗口。
- 验收：用假任务（`sleep 300` 与 `sleep 300 && false` 两个变体）各测 5 次，
  触发误差 ≤2 秒，失败变体 5/5 触发。

### 2.5 定时唤醒

- 实现：`pmset repeat wakeorpoweron`，需管理员。
- 验收：`pmset -g sched` 显示与我们登记的一致；到点真醒（实测一次，不靠推断）。
- 诚实边界：固件级唤醒在部分机型上不生效，做不到 100%，对外只说"设了会尝试"。

### 2.6 电池健康 / 温度 / 高负载归因

- 电池：`ioreg -rc AppleSmartBattery` 取 `CycleCount` / `MaximumCapacity`。
  验收：与系统设置里显示的百分比一致（±1%）。
- 温度：macOS **无公开传感器接口**，走 SMC 读取。这条保持 `部分`，
  并且不许在产品页写"实时监控 CPU 温度"——写"读取常见传感器，机型差异会导致读不到"。
- 高负载归因：与 S2 的进程采集共用，本批只做"谁在烧机器"的最小组合。

## 3. 架构

```
core/            Go。能力抽象 + 每平台一个适配器。唯一的常驻进程。
  capability/    对上暴露的接口：KeepAwake / Lidless / Headless / Watch / Schedule / Battery
  adapter/       darwin / windows / linux / android(ADB)
  action/        ★ 改系统状态的动作登记（见 §4）
helpers/macos/   Swift。只放 Go 干不动的：私有 CoreDisplay 虚拟显示器、（S2 的）Accessibility。
                 以 stdio JSON 被 core 调用，不常驻、不监听端口。
ui/              Wails + TS。不含业务逻辑，关掉窗口不影响守护。
```

三条不可商量的形状：
1. **能力全在 Go 核心**，壳只是视图。关掉界面，守护照常跑。
2. **Swift helper 不常驻**。它的生命周期由 core 管，需要它才起，用完即散 —— 除了电源断言
   必须挂在活着的进程上，所以断言由 core 自己持有（cgo 直调 IOKit），不交给 helper。
3. **不装常驻 root 服务**。提权动作按次申请，用完就结束。

跨平台边界：2.1 / 2.4 / 2.6 三平台同构；2.2 在 Windows 是改电源按钮行为（无需提权）、
Linux 走 logind 配置；2.3 只有 macOS 需要（Win/Linux 无头照常渲染，直接标"原生支持"）。

## 4. 权限模型与动作登记（这条是给整个产品定的，不只 S1）

沿用昱弘网通已经定过并做成硬约束的三条，原样搬：
**要改什么先摆出来 → 用户点过才动手 → 动手前先落盘登记，崩了下次启动能还原。**

落地成一个 `action` 包，每条动作一条 JSONL 记录：

```
{ id, capability, intent, before, cmd, verify, rollback, state, ts }
state: intent → applied → verified → rolled-back / abandoned
```

- 启动时先扫登记：**存在未闭合记录 → 立刻按 `rollback` 还原**，还原成功才继续启动。
  还原动作 `finally` 无条件执行，不询问用户（宁可还原错，不可留一个合盖不睡的黑洞）。
- 提权方式：macOS `osascript ... with administrator privileges`（免费、无需签名、系统弹窗）；
  Windows UAC `runas`；Linux `pkexec`。**三家都不用 sudoers 白名单、不装 daemon。**
- **由弹窗这个形态推出的一条硬约束：改和还原必须在同一次提权里绑定完成。**
  弹窗只有人在屏幕前才点得了，而合盖场景下人恰好不在屏幕前（合盖走开、或就是在远程会话里点的）。
  所以"收尾时再弹一次窗要密码"等于"还原永远不会发生"，标志就永久留在 1 —— 这正是本条禁止的状态。
  落地形态：一次授权起一个提权子进程，由它负责开、盯到期、还原、必要时补睡；
  未提权的主进程只用一个取消标记文件跟它通信（本机实测踩过，见 §7 20:58 那次作废的 run）。
- 同一处推论：**命令行里的 `sudo` 提示对远程的人不可见**，所以产品侧一律走系统弹窗，
  脚本侧留免密 sudo 票据可用时优先复用它，都是为了"不要求人必须在屏幕前"。
- 登记文件全本机，无上报。

## 6. 界面形状

常驻是 Go 进程（几十 MB），菜单栏/托盘一个图标，点开才起 WebView 窗口。
主屏不是列表，是**当前状态**：现在谁在阻止休眠、合盖保护开没开、有没有任务在盯、
上一次跑完是什么、机器温度。四块都能直接操作，不做二级菜单找入口。
需要提权的按钮，点之前先把"要改哪一项、改完怎么还原"写在这个按钮上方，不是弹一个只有"确定/取消"的框。

## 7. 测试

- **单元**：`capability` 接口 mock，动作状态机全路径（含崩溃恢复、重复登记、还原失败）。
- **真机验收矩阵**（这条是硬要求，缺一个都不算过）：
  macOS 15 / 26 × 有头 / 无头 × 开盖 / 合盖 × 市电 / 电池 × 正常退出 / `kill -9`。
  Windows 11 / Linux（一个发行版）各跑 2.1 / 2.4 / 2.6。
- **合盖实测流程**（§2.2 的阻塞项，需要老板在这台 M4 Max 上配合）：
  ①开 disablesleep ②起一个持续输出帧的任务 ③合盖 ④等 3 分钟 ⑤开盖读
  `pmset -g log | grep -c "Entering Sleep"` 与任务帧数。
  **对照组必须同时跑**：不开 disablesleep 同样流程，否则帧数没掉也说明不了问题。
- 上面这套已经做成脚本，不用手搓命令：`tools/lidprobe/lidprobe.sh 3`（实验组，收尾无条件还原）、
  `tools/lidprobe/lidprobe.sh 3 --control`（对照组，全程不改设置）。两组各跑一次，
  报告落在 `tools/lidprobe/输出/<时间戳>/报告.md`，判据直接取本机 `pmset -g log` 里
  **时间戳落在窗口内的** `due to 'Clamshell Sleep'` 条数 —— 本机 09-21 那次开机以来一直有存量，
  也就是说"合盖会睡"在这台机器上是被记录过的事实，不需要靠感觉判断"好像没睡"。
  采集与算结论是分开的：任何一轮跑完（哪怕中途退了）都可以用
  `tools/lidprobe/analyze.sh 输出/<时间戳>` 重算，不碰机器设置。
  每 2 秒另采一次 `ioreg` 的盖子开合与 `SleepDisabled` 实际取值，
  **合盖时长不足窗口 80% 的 run 直接判不作数**。
  **对照组报不出睡眠，就不要拿实验组的结果下结论。**
- **第二轮对照就是这样被判废的**（2026-09-25 20:33）：老板远程连着干活，一合盖就双方掉线，
  于是只合了约 2 秒 —— 89 个采样里 1 个 Yes、零睡眠事件、心跳零断档。
  这不是判据看不见合盖睡眠，是这次压根没测；门槛若只问"合没合过"就会把这种 run 放过去。
  这条同时是产品约束：**跑合盖实验等于打断老板的远程会话**，跑之前要说清最坏情况
  （掉线几分钟、开盖即回）并一次跑够时长，别让人被断两次。
- **对照组已跑过并通过**（2026-09-25 20:25，本机 M4 Max）：3 分钟窗口内
  `due to 'Clamshell Sleep'` 由 13 → **14**，同时心跳出现一处 **4 秒**断档，两个独立信号对上。
  也就是说这套判据的灵敏度是**秒级**——合盖四秒钟就报得出来。
  所以实验组若真挡住合盖，"零新增事件"是有分量的负结果，不是"其实已经挡住，只是睡过去一小会儿没醒"。
  副产品一条线索：合盖后紧接着一帧抓屏从 2.0MB 涨到 19.8MB —— **这条线索后面被证伪并查清了，见下**。
- **实验组第一轮已跑（2026-09-25 20:47，本机 M4 Max，`SleepDisabled=1`）**：
  盖子实际合上 **82 秒**（41 个 `AppleClamshellState=Yes` 采样），这 82 秒里
  `due to 'Clamshell Sleep'` **14 → 14，零新增**；含全部原因的进入睡眠事件**零新增**；
  心跳 182 个采样、最大间隔 **2 秒**（就是它自己的 1 秒节奏）；
  且**合盖期间 `SleepDisabled` 全程为 1、一次都没回落**（旧口径报的"变化 1 次"是假的 ——
  盯梢比 `disablesleep 1` 早起步几秒，那几秒天然是 0，口径已改成只统计盖子合着的那一段）。
  老板侧同时确认：**合上盖子之后远程照样连得上**，这就是产品口径那一条过了。
  判据分档由此定下来：对照实测"合盖→真睡着"的延迟只有 ≤4 秒，
  所以**合盖 30 秒以上仍零睡眠事件**已是十几倍于延迟的正证据（记「短时」档），
  跑满窗口 80% 才记「满格」；低于 30 秒一律不作数（第二轮对照就是这样废的）。
- **锁屏 ≠ 睡眠，这条是用帧数据答的**：合盖后头 ~36 秒抓屏与合盖前完全一致
  （均亮 233、2.1–2.3MB），说明合盖这个动作对画面管线毫无影响；
  第 39 秒起跳到均亮 44–49、18.4–19MB 且逐帧微变 —— 那是**老板关掉远程窗口后系统进了锁屏**
  （模糊壁纸=高熵=文件大），**纯黑像素占比 0.0%**，不是黑屏也不是断渲染。
  也就是说"远程一关就退回锁定桌面"是登录窗口的正常行为，采集循环整程没断就是任务没断。
  那条 19.8MB 的"线索"到此结案：是锁屏内容，不是显示模式变了。
- **实验组第二轮（2026-09-25 20:58）作废，作废原因是工具自己的洞，不是能力问题**：
  老板答了第一个授权框后没再动，脚本卡在"开 disablesleep"那一步等**第二个**框，
  于是整轮 `SleepDisabled` 全程为 0（`flag.tsv` 253 个采样全 0，仅 1 个盖子 Yes）——
  这一次什么都没测到，也不该拿去当"开不起来"的证据。
  更严重的是旧写法收尾要**第三个**框：那时人已经合盖走开，框没人点 → 标志会留在 1。
  修法是拆出 `tools/lidprobe/lidroot.sh`：一次授权负责到底（开 → 盯到期 → 还原 → 仍合盖则补睡），
  主进程改为轮询取值确认到 1 才起跑（最多等 90 秒，给人伸手点窗的时间），
  等不到就写取消标记 + 判"本次不跑、机器状态未改动"——
  万一人是 90 秒之后才点的，root 半边一看到标记立刻还原，不会攥到兜底到期。
  这一条已经升成 §4 的硬约束，产品实现必须照做，不是脚本层的临时绕法。
- **实验组第三轮（2026-09-25 21:27）也没测成正题，但它证出了坑 #2**：
  起跑 13 秒后取消标记被写了一次，root 半边当场把 `disablesleep` 还原成 0；
  而老板那时已经合上盖子，于是"合盖那一刻 flag=1、随后 172 秒 flag=0"这一段
  既没测成"开着挡不挡得住"（开着的时间只有 2 秒），又白捡了一条坑 #2 的本机实测（已回填 §2.2）。
  **写那个标记的是谁，本机没能复现** —— 目录只有一个、进程当时只剩采样，
  最像的解释是有两轮同秒起跑、共用了同一个取消标记文件。
  没有把这条含糊过去，而是把两类成因都堵上：`tools/lidprobe/.run.lock` 单实例锁（已实测能挡下第二轮），
  取消标记改成按 pid 分开（`cancel.$$`），就算真撞了也踩不动对方的还原。
- **工具因此拆成三件事，各自能单独重算**：`lidprobe.sh`（采集）、`lidroot.sh`（一次授权的 root 半边）、
  `analyze.sh`（只读盘算结论）。拆分的原因是这一轮主进程提前退出后，
  盘上躺着 292 个心跳和 87 个合盖采样，**报告却一个字都没有** —— 分析和采集绑死，
  一次早退就把证据哑掉了。现在早退也会出报告（`EXIT`/`INT`/`TERM`/**`HUP`** 都接住，
  HUP 那条尤其要紧：终端一关默认动作是直接收进程，那样 disablesleep 就被攥在 1 里没人还原）。
  另外判据改成**按日志自带时间戳数进窗口**，不再用"事后总数 − 基线"：
  隔一小时重算，增量口径会把窗口之外的其它睡眠一起算进来，那就不是这一轮的数了。
  新口径重算了之前四份数据，与当场结论一致（对照那轮仍是 Clamshell +1、心跳断档 4 秒）。
- **五处顺带修的工程洞**（全部本机实测撞出来，不是推测）：
  ① `pmset -a disablesleep 1` 在非 root 下会把 `must be run as root` 打到 stderr **却退出 0**，
  所以 `|| exit 1` 是空的、会报假成功 —— 一律改成"读回来的值"校验（现在非 root 冒烟正确报
  `开不了 disablesleep（当前 0），退出` 退出码 1）。
  ② **`screencapture` 拒写以点开头的文件名，却同样退出 0** —— 抓屏循环因此整轮记成"成功但 0 字节"，
  目录里一张图都没有。改成非点文件 + 判文件真在不在（`-s`），实测一帧 1.87MB 正常落盘。
  ③ 主进程一旦卡住，采样子进程无人收尾：那次空转 8 分钟，抓屏循环吃掉 **268MB**
  （每张全屏 PNG ≈ 5.3MB）—— 三个采样循环现在都带硬到期，抓屏每张只记大小、每 6 张留一张，
  1 分钟一档实测整轮 3.6MB。
  ④ **`pmset -g log` 一次要 10 秒**（本机实测），旧写法连着调两次，
  于是"起跑"到"落基线"之间有 20 秒空白 —— 上一轮那 13 秒的蹊跷时间差就是这么来的。
  现在整轮只抓一次快照，几个计数都从这一份里数。
  ⑤ 提权那半边一律用绝对路径（`/usr/bin/pmset`、`/usr/sbin/ioreg` 等），
  因为 `do shell script` 给的环境 PATH 只有 `/bin:/sbin:/usr/bin:/usr/sbin` 这一小圈，
  本机日常 PATH 里的 pyenv/homebrew 一个都不在里面。
- 仍待补的（这三条现在都还没有实测，不许写进对外文案）：
  ① **满格档一次都没有**：要的是"合盖期间 `SleepDisabled=1` 连续覆盖 ≥ 窗口 80%（3 分钟档 = 132 秒）"
  且零睡眠事件。现在最强的一轮是短时档（开着的 82 秒）和坑 #2 那轮的 2 秒，都不算满格；
  ② **重启 / 待机之后 `SleepDisabled` 还在不在**（二手证据两边说法冲突）；
  ③ §5.2 的合盖热降频与 §2.3 的**真实 Metal/ffmpeg 帧数一致性** ——
   framebuffer 活着不等于 GPU 吞吐没变，这条只能等实现完再量。
- 反证要求：任何一条能力，先写"它失败长什么样"的检查，再写实现。
  跑完还绿的轮次要回去查是不是覆盖有洞。
